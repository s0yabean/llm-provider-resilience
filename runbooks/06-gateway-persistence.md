# Runbook: gateway works now but will not survive a reboot

A gateway started by hand dies with the machine or the container. The usual
fix is to install it as a service, but that depends on what manages processes.

## On a normal host

Install it as a systemd (Linux) or launchd (macOS) service with restart on
failure. Most agent frameworks ship an `install` command for this.

## Inside a container

There is usually no systemd. Service installers often refuse and tell you to
use the container runtime's restart policy (`--restart unless-stopped`) or the
supervisor the image already runs (supervisord, s6, runit). Look before adding
anything:

```bash
ps -ef | grep -E "supervisord|s6-svscan|runsv" | grep -v grep
supervisorctl status
```

## Classic trap: the supervised service is "RUNNING" but never started the gateway

Symptom: the supervisor reports the gateway as RUNNING, yet the only process
actually connected to the chat platform is one you started by hand.

Cause: a user / `HOME` mismatch. A wrapper script typically waits for the
config to exist, then starts the gateway:

```bash
until [ -f "$HOME/.agent/config.yaml" ]; do sleep 30; done
exec agent gateway run
```

If the supervisor runs the program as a user whose `HOME` is not where the
config lives, the wrapper waits forever. The tell: the wrapper's only child is
`sleep`, not the gateway.

```bash
WPID=$(pgrep -f "<wrapper script name>")
ps --ppid "$WPID" -o pid,cmd
```

## Fix

1. Back up the supervisor program file.
2. Run the program as the user who owns the config, with `HOME` set explicitly:
   ```ini
   [program:agent-gateway]
   command=/usr/local/bin/agent-gateway-wrapper
   user=<config owner>
   environment=HOME="<that user's home>"
   autorestart=true
   stopsignal=TERM
   ```
3. Stop the hand-started gateway first. Two pollers on one bot token fight each other.
4. `supervisorctl reread && supervisorctl update && supervisorctl restart agent-gateway`
5. Confirm exactly one gateway process and a clean connect in the log.

If the supervisor config is generated by the platform image, an image rebuild
may revert the fix. Keep this runbook next to the deployment so it is quick to redo.
